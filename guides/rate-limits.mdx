Ory Network applies rate limiting to protect all customers from abuse, prevent service disruptions, and ensure fair resource allocation. There are two independent layers of rate limiting: project-level limits based on your subscription plan and environment, and endpoint-level limits that protect specific APIs against attack patterns regardless of your plan.

## How project rate limits work

Project rate limits depend on two factors:

1. **Workspace subscription plan** — Developer, Production, Growth, or Enterprise.
2. **Project environment** — Production, Staging, or Development.

Each policy defines two thresholds:

- **Burst limit** — maximum requests per second (rps), allowing short traffic spikes.
- **Sustained limit** — maximum requests per minute (rpm), enforcing consistent throughput over time.

Higher-risk endpoints (such as registration, recovery, and admin identity management) have stricter limits than general API traffic.

## Endpoint-based rate limits

Endpoint-based limits operate independently of project limits and protect specific APIs against attack patterns such as brute-force and credential stuffing.

### Volumetric limits

Ory analyzes request patterns using source IP addresses, JA3/JA4 TLS fingerprints, request frequency, authentication status, and HTTP method to detect and block volumetric attacks.

### Inflight limits

Inflight limits prevent concurrent requests to the same resource, eliminating race conditions on write operations. These limits are keyed on `{project_id} + {full_path}`.

| Endpoint | Methods | Status |
|---|---|---|
| `/admin/identities` | `POST`, `PATCH` | Enforced — blocks concurrent requests |
| `/admin/identities/{id}` | `PUT`, `PATCH`, `DELETE` | Enforced — blocks concurrent requests |
| `/admin/identities/{id}/credentials/{type}` | `DELETE` | Enforced — blocks concurrent requests |
| `/admin/identities/{id}/sessions` | `DELETE` | Enforced — blocks concurrent requests |
| `/admin/sessions/{id}` | `DELETE` | Report-only |
| `/admin/sessions/{id}/extend` | `PATCH` | Report-only |
| `/self-service/recovery` | `POST` | Report-only |

<Note>
  Report-only endpoints log violations but do not block requests yet. `GET`, `OPTIONS`, and `HEAD` requests are exempt from inflight limits.
</Note>

## Handle 429 responses

When you exceed a rate limit, Ory returns HTTP `429 Too Many Requests`. Implement exponential backoff with jitter in your client to handle these responses gracefully:

```javascript title="retry-with-backoff.js"
async function fetchWithRetry(url, options, maxRetries = 3) {
  for (let attempt = 0; attempt < maxRetries; attempt++) {
    const response = await fetch(url, options);

    if (response.status !== 429) {
      return response;
    }

    const retryAfter = response.headers.get("Retry-After");
    const delay = retryAfter
      ? parseInt(retryAfter, 10) * 1000
      : Math.min(1000 * 2 ** attempt + Math.random() * 100, 30000);

    await new Promise((resolve) => setTimeout(resolve, delay));
  }

  throw new Error("Max retries exceeded");
}
```

## Best practices

**Cache session checks.** The `/sessions/whoami` endpoint is the most commonly rate-limited. Cache session data on your server for the lifetime of your own request context rather than calling Ory on every API request.

**Use batch admin APIs.** When creating or updating many identities, use `POST /admin/identities` (bulk) rather than individual creates in a tight loop.

**Separate environments properly.** Development and Staging environments share lower limits regardless of plan. Do not run load tests or stress tests against Development or Staging — use a dedicated Production environment project.

**Respect the `Retry-After` header.** When present, this header tells you exactly how long to wait before retrying. Honor it rather than retrying immediately.

**Upgrade your plan for higher limits.** If your Production workload consistently approaches or hits limits on the Production plan, consider upgrading to Growth or Enterprise, or [contact Ory](https://ory.com/contact) for custom limits.
