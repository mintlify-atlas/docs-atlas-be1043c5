Multi-factor authentication (MFA) adds a second verification step after a user's primary login, making it significantly harder for an attacker to compromise an account even if the password is known or leaked. Ory Identities supports several second-factor methods that you can enable independently based on your security requirements.

## How MFA works in Ory

Ory tracks the strength of authentication using the **Authenticator Assurance Level (AAL)**:

- `aal1` — the user completed one authentication factor (for example, password or social sign-in)
- `aal2` — the user completed the first factor and a second factor (for example, password + TOTP)

The current AAL is available on every session object under `authenticator_assurance_level`. You can use this value to gate access to sensitive operations.

<Note>
Completing two first factors (for example, password and OIDC social sign-in) does **not** yield `aal2`. Only a combination of a first factor and a dedicated second factor reaches `aal2`.
</Note>

### Authentication Method Reference (AMR)

The session also carries an `authentication_methods` array listing every method the user has completed during the session's lifetime:

```json
{
  "authenticator_assurance_level": "aal2",
  "authentication_methods": [
    { "method": "password", "aal": "aal1", "completed_at": "2024-01-15T09:37:53Z" },
    { "method": "totp",     "aal": "aal2", "completed_at": "2024-01-15T09:38:10Z" }
  ]
}
```

## Available MFA methods

<CardGroup cols={2}>
  <Card title="TOTP (Google Authenticator)" icon="clock">

## TOTP (Time-based one-time passwords)

TOTP generates a short numeric code (usually 6 digits) that is valid for 30 seconds. Users pair a TOTP app with their account by scanning a QR code, then enter the rotating code as their second factor.

Compatible apps include Google Authenticator, Authy, LastPass Authenticator, and FreeOTP.

### Enable TOTP

<Tabs>
  <Tab title="Ory Console">
    <Steps>
      <Step title="Open MFA settings">
        Log in to the [Ory Console](https://console.ory.sh/), select your project, and go to **Authentication** > **Two-factor auth**.
      </Step>
      <Step title="Enable TOTP">
        In the **TOTP Authenticator App** section, toggle the switch to enable TOTP.
      </Step>
      <Step title="Set the display name">
        Enter a **Display Name** — this is the issuer name users see in their authenticator app when generating codes.
      </Step>
      <Step title="Save">
        Click **Save**.
      </Step>
    </Steps>
  </Tab>
  <Tab title="Ory CLI">
    ```shell
    # Get your current identity config
    ory get identity-config \
      --project <project-id> \
      --workspace <workspace-id> \
      --format yaml > identity-config.yaml
    ```

    Add the following to `identity-config.yaml`:

    ```yaml
    selfservice:
      methods:
        totp:
          enabled: true
          config:
            issuer: YourApp.com
    ```

    ```shell
    ory update identity-config \
      --project <project-id> \
      --workspace <workspace-id> \
      --file identity-config.yaml
    ```
  </Tab>
</Tabs>

### User experience

After TOTP is enabled in your project, each user must pair their account individually:

1. The user signs in to their account and navigates to **Account Settings** > **Authenticator App**.
2. They scan the QR code displayed on screen with their TOTP app.
3. The TOTP app begins generating codes. The user enters the current code to confirm pairing.
4. On subsequent logins, after entering their password, the user is prompted to enter the 6-digit TOTP code.

<Tip>
Users see the `issuer` name you configured when they look at their TOTP app. Use a clear, recognizable name such as your application or company name.
</Tip>

## WebAuthn and hardware tokens

WebAuthn uses the [Web Authentication API](https://developer.mozilla.org/en-US/docs/Web/API/Web_Authentication_API) to authenticate users with public-key cryptography. It supports both on-device biometric authenticators (TouchID, FaceID, Windows Hello) and external hardware tokens (YubiKey, NFC devices, BLE devices).

### Enable WebAuthn for MFA

<Tabs>
  <Tab title="Ory Console">
    <Steps>
      <Step title="Open MFA settings">
        In the Ory Console, navigate to **Authentication** > **Two-factor auth**.
      </Step>
      <Step title="Enable WebAuthn">
        In the **WebAuthn** section, toggle the switch to enable it.
      </Step>
      <Step title="Configure your domain">
        Set the **hostname** to your top-level domain (for example, `app.example.com`).

        Set the **origin** to the exact URL of the page that prompts the user for WebAuthn, including scheme, host, and port (for example, `https://auth.example.com:4455`).
      </Step>
      <Step title="Save">
        Click **Save**.
      </Step>
    </Steps>
  </Tab>
  <Tab title="Ory CLI">
    ```yaml title="identity-config.yaml"
    selfservice:
      methods:
        webauthn:
          enabled: true
          config:
            passwordless: false
            rp:
              display_name: My App
              id: example.com
              origins:
                - https://auth.example.com:4455
    ```

    ```shell
    ory update identity-config \
      --project <project-id> \
      --workspace <workspace-id> \
      --file identity-config.yaml
    ```
  </Tab>
</Tabs>

<Warning>
WebAuthn is a browser-only standard. It does not work in native mobile apps. WebAuthn credentials are also tied to a specific domain — changing the `id` or `origin` will break existing users' credentials.
</Warning>

### User experience

When a user triggers a WebAuthn-protected action, the browser shows a native prompt asking them to confirm their identity with the registered authenticator — for example, by touching a fingerprint reader or pressing the button on a YubiKey.

## Lookup secrets (backup codes)

Lookup secrets are a set of one-time backup codes that users generate and store securely. They serve as a fallback when the primary second factor is unavailable — for example, when a phone is lost or a hardware token is broken.

Each code is valid for single use only. When a user generates a new set of codes, all previously generated codes become invalid.

### Enable lookup secrets

<Tabs>
  <Tab title="Ory Console">
    Navigate to **Authentication** > **Two-factor auth**, find the **Lookup Secrets** section, and toggle the switch to enable it. Click **Save**.
  </Tab>
  <Tab title="Ory CLI">
    ```yaml title="identity-config.yaml"
    selfservice:
      methods:
        lookup_secret:
          enabled: true
    ```

    ```shell
    ory update identity-config \
      --project <project-id> \
      --workspace <workspace-id> \
      --file identity-config.yaml
    ```
  </Tab>
</Tabs>

### User experience

After lookup secrets are enabled:

1. The user navigates to their account settings and generates a set of backup codes.
2. Ory displays the codes once. The user must store them securely (for example, in a password manager).
3. The user confirms receipt by entering one of the codes. This step requires a privileged session.
4. When completing the second factor during login, the user can choose to enter a backup code instead of their usual second factor.

<Warning>
Codes are only activated after the user confirms they received them. Once a code is used, it cannot be reused.
</Warning>

## Checking AAL in your app

After a user logs in, check the `authenticator_assurance_level` field in the session to determine what level of authentication they have completed. Use this to enforce access policies:

```bash
curl -H "Cookie: ory_session_...=..." \
  "https://$PROJECT_SLUG.projects.oryapis.com/sessions/whoami"
```

```json
{
  "active": true,
  "authenticator_assurance_level": "aal2",
  "authentication_methods": [
    { "method": "password", "aal": "aal1" },
    { "method": "totp",     "aal": "aal2" }
  ]
}
```

If the session is `aal1` but your endpoint requires `aal2`, redirect the user to the login flow with `aal=aal2` to trigger the second-factor challenge.
